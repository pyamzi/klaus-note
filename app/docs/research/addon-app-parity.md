# KlausNote: Anki foundation first, then add-on parity

Priority clarified by the user on 2026-10-06: use [upstream Anki](https://github.com/ankitects/anki) as the primary reference, build and verify the app's Anki foundation first, then layer current KlausNote for Anki features on top before extending the new lecture workflow. The pinned `vendor/anki` source defines core behavior; the add-on defines Klaus-specific extensions. Implementation uses the app's Svelte/shadcn UI and Rust bridge. See [the reference order](../../AGENTS.md#reference-and-delivery-order). This is an inventory and delivery checklist, not a claim of completed migration.

## Delivery order

1. **Anki foundation and main workflows:** inspect upstream behavior, close bridge/shell gaps, then verify Home/decks, Study, Add and Browse, including keyboard/focus, editing/media, undo and native Anki actions against Anki itself. Verify relevant core data operations before extending these workflows.
2. **Add-on workspace and authoring:** layer dashboard/widgets and workspace navigation onto the verified foundation, then one shared PDF reader, annotations and file synchronization; hosted reader/editor panes, cropping and image occlusion. Use the add-on as the reference for these extensions.
3. **Intelligence and settings:** local runtime/models, OCR, indexes/matching, tags, retention, curated decks, background tasks and external tools/MCP.
4. **Parity acceptance:** compare every inventory item with the current add-on in real Anki and the standalone app. Record both appearance and behavior evidence. Preserve any user data during migration tests.
5. **Then extend lectures:** return to the approved transcription, slide/sheet navigation and PDF transcript-note workflow using those shared foundations.

The order is dependency-based; no current feature is silently excluded. Features implemented by third-party Anki add-ons need an explicit compatibility decision if encountered, rather than an assumption that their Python/Qt code runs in Tauri.
